# 当前功能与架构地图

源码核对日期：2026-10-18。本文描述 Windows 工作区的现有实现，不代表服务器已启用这些开关。当前任务约束为 Jev、原问题、仅提示；Laya 暂停。未部署或读取实际群设置。

## 主体是一个有持久化状态的 Go 机器人

一个 Go 进程负责 Bot API 长轮询、入群状态机、私聊控制台、频道处理、预览队列与 HTTP；SQLite 保存每群设置、流程、任务与记录。不需要 Redis、外部任务队列或独立 AI 编排服务。

```text
Telegram 更新 ──► Bot API 客户端 ──► 更新路由
                                      ├─ 入群 / 申请 / 回调 ─► gate 状态机
                                      │                       ├─ 可选 CAS / Jev
                                      │                       └─ 验证题 / 人工 / 收尾动作
                                      ├─ 群命令 / 服务消息 ─► 管理与清理
                                      ├─ 频道转发 / 马甲 ───► channel
                                      └─ 私聊控制台 ───────► 配置 / 来源 / 用户号登录

Mini App ──► HTTP initData 验证 ──► 同一个 gate 状态机
网站 Feed / Sitemap ──► preview 队列 ──► 可选 MTProto 用户号 ──► @WebpageBot

SQLite ◄── 每群设置、gate 状态、步骤位、删除队列、事件、预览任务、用户号会话
```

`internal/app/app.go` 组装组件并管理生命周期；`internal/bot/bot.go` 先处理机器人自身成员变化，再把更新分为 16 个分片，保持同一用户顺序。私聊慢操作使用独立串行队列；入群调度器默认 8 个 worker，按流程加锁。它们是同一进程的并发任务，不是微服务。

CAS 和 Jev 是这个入群状态机里的两个独立可选检查：CAS 关闭就跳过列表查询，Jev 关闭或未配置就跳过资料判断。两者都关闭时，从 `new` 正常进入验证题；不会关闭入群状态机。

| 消息清理 | 加入、离开、置顶等服务消息与命令；删除验证未完成者的发言 | 默认清理加入、离开、命令；后者不判断内容 | `bot/group.go`、`store/` |
| 频道联动 | 取消频道置顶／只留最新；清频道旧置顶且保留管理员置顶；删除并封外部频道马甲 | 默认关闭，独立于 Jev | `channel/channel.go` |
| 欢迎消息 | 通过后按群模板发送欢迎语、按钮，定时清理或临时消息 | 默认关闭 | `gate/deliver.go`、`steps.go` |
| 链接预览刷新 | 手动链接；发现 Feed／Sitemap、抓取、去重与慢速队列；用户号联系 @WebpageBot | 需 MTProto 应用配置和已登录用户号 | `preview/`、`preview/feeds/`、`userbot/` |

除 `cmd/` 外，表内路径均在 `internal/`。新群默认值来自 `store.DefaultSettings()`，不等于已有群设置。源码具备能力不等于真实 Telegram 验收；旧进度文件中的 live 项仍需实际群验收，本次没有替代这些验收。

## 一次入群的判断顺序

直接加入先检查群状态、机器人账号、验证开关、可信豁免与重复事件；需要验证时创建 `new` 流程，立即保存原有限制并临时禁言。调度器随后执行可选 CAS、可选 Jev，再投递题目进入 `challenge`。

答对在本轮 hint 策略下正常进入 `resolving`；答错增加次数并换题，截止时间不延长。次数用尽按群配置移除或转 `review`；求助、投递失败也可转人工。审核／答题超时触发既有规则；若因机器人投递失败无法验证，审核到期按取消处理，避免因该故障惩罚成员。

`resolving` 顺序执行动作、清理、欢迎、记录，各步骤保存完成位，最后 `closed`。状态在 SQLite 中，重启后按 `next_at` 继续。冷却按既有失败记录递增，不由 AI 分数决定时长。

普通入群申请在批准前不是群成员，不需要先群内禁言；题目发到申请联系通道。Guard 有有效 query 和 Web URL 时先发送 Mini App，由同一状态机处理，失效后回退普通申请动作。

## Jev 在哪里影响结果

四项主要风险为无关推广、金融风险、成人推广和管理／官方角色声明；广告排版仅为信息。`Risk` 是四项最大值，不是经校准的联合违规概率。

当前 hint 策略只保存风险值和原因，在流程进入人工审核时显示于审核卡；不设置 `FlagHighRisk`，答对不会因 AI 高分转人工或额外告警。源码仍保留可选 Jev `review`：高分先设置标记，答对后转人工；这不属于本轮启用范围。Jev 超时或失败按无 AI 结果继续验证，不把失败当作安全预测。

**AI 仅提示不等于机器人不执行管理动作。** 验证失败、超时、CAS 命中、频道马甲和管理员命令都有自己的规则。要理解处置来源，应沿 gate outcome 或命令记录追溯。

实际入群路径尝试 `GetChat` 获取简介，申请事件已有的简介会作为查询失败时的回退；直接入群拿不到简介时仍可能只凭名字和用户名判断。群标题会传入，当前调用没有补充群描述。这解释了为何专门评测空简介昵称。

## 当前没有做什么

- 没有将正常群消息送入 Jev 审核广告／敏感内容，也没有持续聊天内容审查流水线。
- 没有根据自然语言指令让 AI 自主调用踢人／封禁 API。
- 没有已经上线的独立“多群 AI 决策 REST API”；当前 HTTP 路由是健康检查与 Mini App 验证。
- Laya 接入与历史证据保留，评估和部署推进暂停；无自动切换或云端回退。

## 消融进度与后续候选

用户选定 Jev 提示开／关，已完成 [324 对本地回放](../guide/jev-hint-ablation)：终态与管理动作一致，提示只增加资料观察与出题前等待。实际群设置不变；其余模块尚未消融。

| 候选 | 独立对照方式 | 应观察什么 |
|---|---|---|
| Jev 提示（已完成） | 同一事件回放 `off` / `hint`，原问题不变 | 324 对处置一致；审核卡增加提示，检查占用原验证窗口 |
| CAS | 假 Bot API 与固定列表回放，开／关 CAS | 列表命中处置、误命中影响、超时降级 |
| 验证与人工回退 | 固定加入和答题／超时事件，比较策略 | 完成率、错误移除、重试恢复；资料标签不能代替验证码效果 |
| 突击防护 | 固定加入突发序列，开／关 raid | 队列等待、消息数量、时限和收尾 |
| 频道／清理 | 固定消息与发送者身份回放，逐开关比较 | 删除／取消置顶数量、保留管理员消息 |
| 预览分支 | 同一订阅任务启用／禁用可选用户号或队列 | 主验证延迟、重试、吞吐与外部调用 |

持久化、授权和状态一致性是正确性基础，不作为普通功能开关消融。Jev 消融使用本地假 API／固定回放，CAS 条件在每对两侧相同；未执行其他模块的消融，也未部署。

本轮 [96 条资料评测](../guide/jev-fresh96) 只支持 AI 资料判断这一层，不能证明验证码、突击防护或频道管理的整体效果。
