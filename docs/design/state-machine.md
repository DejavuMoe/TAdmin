# 入群状态机

每一次入群验证都是 `gates` 表中的一行。它在五个状态之间流转，每一步都先落库、再执行外部动作。点击节点查看细节，或播放一个场景：

## 为什么能随时重启

- **先写库，后动作。** 入群事件先成为一行 `new` 记录，再去禁言；禁言前还会先保存成员原有的权限，崩溃也不会把 TAdmin 自己的禁言误当成管理员限制。
- **步骤位图。** `resolving` 阶段的每个步骤（动作、清理、欢迎、记录）完成后立刻写入位图，重启后只做没做完的部分，欢迎语不会重复发送。
- **幂等动作。** 解除限制、移出、批准都可以安全地重复执行；“消息已不存在”“用户已离开”等错误被视为成功。
- **禁言自带到期。** 即使 TAdmin 停机数天，禁言也会在截止时间 + 10 分钟（加上审核窗口）后自动解除；恢复后调度器再把超时的流程收尾。

## 调度与并发

- 调度器按 `next_at` 取到期流程，最多 8 个 worker 并行；同一流程由按 ID 分片的锁串行，按钮、Mini App 请求和调度器互不踩踏。
- 暂停一个群只阻止**新建**流程，已有流程照常收尾，不存在“暂停群占满批次、饿死别的群”的问题。
- 定时删除消息在独立的 goroutine 中执行，遇到限流就停下留待下一轮，从不拖慢入群处理。

## 重试策略

| 失败类型 | 处理 |
|---|---|
| 网络错误、5xx、429 | 指数退避（2 秒起，最多 5 分钟，遵守 `retry_after`），最多 8 次 |
| 400 / 403 权限类错误 | 不重试，私聊所有者告警（同类 10 分钟一次） |
| 目标已不存在（消息被删、用户离开） | 视为完成 |
| 投递题目永久失败 | 直接转人工审核；审核到期放行，不惩罚用户 |

::: warning 带到期时间的调用
`banChatMember` 与 `restrictChatMember` 携带绝对的 `until_date`。Telegram 把距现在不足 30 秒的时间视为**永久**，所以这两个方法在客户端内部**不重试 429**，而是交回状态机，由它在下一次尝试时重新计算到期时间。最短封禁 2 分钟，对时钟偏差也留足余量。
:::
