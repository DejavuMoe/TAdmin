# Jev 提示开／关：入群状态机消融

2026-10-18。Jev 保留当前原问题和阈值，只在本地成对回放 `off` / `hint`。CAS 和 Jev 是同一个入群状态机里的两个可选检查环节；两者都关闭时仍正常验证。本轮没有修改运行时逻辑、群设置或部署服务器，Laya 继续暂停。

## 结果

**324 对、648 次流程全部通过，终态和 Telegram 管理动作参数没有差异。**

| 对照 | Jev off | Jev hint |
|---|---:|---:|
| 正常作答终态 `pass` | 312 | 312 |
| 三次答错 `fail` | 3 | 3 |
| 截止后未完成 `timeout` | 3 | 3 |
| 求助后管理员批准 `approve` | 3 | 3 |
| CAS 命中 `cas` | 3 | 3 |
| 获取资料／请求 Jev | 0／0 | 318／318 |
| 成功保存风险与原因 | 0 | 309 |
| 审核卡出现 AI 提示 | 0 | 3 |
| CAS 调用 | 9 | 9 |

318 次是假 Jev 请求；HTTP 503、缺答和超时各 3 次，故成功保存 309 次。另有 3 次未配置 assessor 和 3 次 CAS 命中，在 hint 下也不调用模型。CAS 清白、故障、命中三个条件分别保持在每对的两侧一致，不构成 CAS 模块消融。

人工审核卡的提示只在已经进入审核时显示；成功答题不会因高分额外发出告警或转人工。本轮三个求助场景的 hint 卡片多出 `AI 资料风险：99%（promotion）`；`promotion` 是代码从最高分选出的标签，五项同为 0.99 时按固定顺序选第一项，不是模型生成的解释。

## 实验如何控制变量

- 执行前写定 `deploy/laya/eval/protocol-jev-hint-ablation.md`，运行报告保存协议和输入、源码、测试的 SHA256。
- 复用新 96 条中英文资料及之前 `jev-1.13.0` 的真实响应，不重问模型，不改标签，避免把重复推理的波动混入开关差异。
- 96 条分别走直接入群、普通申请、Guard，各做一组 `off` / `hint`，合计 288 对；这部分全部固定为正确作答，验证模型分数不会越权改变验证结果。
- 每种入口再跑三次答错、超时、求助后批准、HTTP 503、缺答、HTTP 超时、无 assessor、CAS 清白／故障／命中、2 秒检查延迟、重建引擎后继续，合计 36 对。
- 使用现有内存 SQLite、假 Bot API、真实 Jev HTTP 适配器。逐请求校验当前问题、账号 state、群标题和模型名与冻结输入一致；标签、语言标签、切片和 Telegram ID 不进入模型 state。
- 两侧题目种子、事件时间、验证配置相同；比较最终状态、次数、标记、执行者，以及禁言／解禁／封禁／批准／拒绝的全部 API 参数。风险值、原因、额外资料读取是允许的观测差异。

关闭侧是“没有 AI 观察”，不能计为模型预测安全，也不将关闭侧的风险覆盖率当作分类准确率。

## 提示增加了什么

冻结资料在三种入口的 288 次 hint 回放均保存了与原响应四项最大值一致的风险及原因，off 则保持 `Risk=-1`、原因空。没有设置 `FlagHighRisk`，已完成检查的流程在重建引擎后不重新请求 Jev。

语义质量仍来自 [原 96 条报告](./jev-fresh96)，本次没有新的推理证据：

- 0.85 下正常资料主要风险误报 0/48；风险资料提示覆盖 37/48，中文 16/24、英文 21/24。
- 空简介昵称风险提示覆盖 22/32，中文 9/16、英文 13/16。
- 反诈否定句主要风险误报 0/12；0.5 下仍存在细分归因错误。

这些提示不会自动拦截风险账号：本轮包括高风险资料的正确作答，在 off 和 hint 下都通过。是否帮助管理员做出更好的判断，需要后续人工复核证据；本轮不能证明。

## 等待时间

| 观察 | off | hint | 证据性质 |
|---|---|---|---|
| 注入 2 秒检查耗时后可作答 | 加入后 0 秒 | 加入后 2 秒 | 受控虚拟时钟，三个入口一致 |
| 上述场景剩余答题时间 | 180 秒 | 178 秒 | 原截止不延长 |
| Jev 不响应 | 无模型请求 | 约 4.01–4.02 秒后降级，照常验证 | 本轮真实 HTTP 取消，假服务器不返回 |
| 既有 96 次本地代理请求 | 无 | 中位 362 ms，P95 492 ms，最大 1,446 ms | 复用前轮计时，非本轮线上测量 |

直接入群先禁言，再由调度器做检查；普通申请在投递题目前检查；Guard 先发送 Mini App，再准备状态机中的验证题。Guard 的“可作答时间”不等于首次弹出 Mini App 的时间。

HTTP 适配器默认超时 4 秒；入群检查给 `GetChat` 与 Jev 共用 5 秒上层预算。这里证明的是检查在出题前占用时间，未测并发排队、管理员操作时间或真实服务器吞吐。
